## 01 产品定位、外贸痛点与核心设计哲学 {#s1}

### 1.1 为什么传统外贸软件难以同时做好「正确」与「智能」

中国 B2B 出口贸易是一类典型的**高约束、多往返、多口径、强合规**业务，远非简单的进销存流水线：

- **业务非单向线性**：客户询价、工厂寻源、多轮报价与改价、样衣与规格变更、部分分批下单、预收预付先于出运、直发与本仓混合履约、以及售后索赔退货会交错发生，任何单据变更都会波及下游采购、出运、合规与结算。
- **价、税、汇、量极易失真**：数量精度、单价精度、跨币种汇率方向与用途、含税与未税反算、阶梯价与 MOQ、最大余数法付款分期、以及出口退税与采购进项税的分离核算，若混用浮点数或由表格／界面临时拼凑，极易产生无法解释的对账差额。
- **人、货、票、款、权五流分离**：供应商上报发货不等于我方核实交付；海关放行不等于实际离境或客户验收；系统内商业收款核销不等于行政意义的出口收汇核销；销售签单不能自己审批低毛利或放行客户信用。
- **通用对话式 AI 无法直接落入交易核心**：大模型擅长阅读非结构化的 PDF／Excel／文本询价并起草方案，但存在幻觉、越权、提示词注入、反复重试造成重复下单，以及“口头宣称已完成”等风险，绝不允许直接修改交易表或替代人工签核。

## 02 外贸全链路业务蓝图与 18 个能力域 {#s2}

Brant 将完整的外贸运营拆解为 **5 条业务运营流**、**18 个限界上下文**（4 个核心域、1 个增强支撑域、11 个支撑域、1 个通用域、1 个可选包）以及顶层的 **AI 能力层**与底层的**确定性工程底座**。所有上下文均为模块化单体内的逻辑与数据边界，支持按公司和进程开关按需装配。

{{pm_panorama fig="FIG 01"}}

### 2.1 五大业务运营流详解

1. **流 ① · 商机与客户需求（`CRM` → `EVD` → `INQ`）**
   - **`CRM`（轻量客户关系 · 可选包）**：管理线索捕获、商机推进与客户跟进。通过 `brant-api -disable-crm` 或 `BRANT_DISABLE_CRM=true` 可整包关闭（满足 `BC-AT24`：关闭 CRM 后核心交易链完整可运行，带商机引用的询价被明确拒绝）。
   - **`EVD`（来源证据与业务文件）**：建立来源四层身份、管理客户原始询价文件（Text／PDF／XLSX）及正式单据字节留证，确保后续任何单据都能追溯至原始证据 SHA-256。
   - **`INQ`（客户询价）**：保存带有原文坐标定位的询价草稿，经人工对照原始文件核实范围与缺失字段后确认为 `ready`（`BC-AT27`），严禁通过凑数掩盖源文件数量冲突。

2. **流 ② · 寻源、精确核价与报价审批（`SUP` → `CST` → `TRD 报价`）**
   - **`SUP`（供应寻源与供应条件）**：向多家供应商发起询价，由独立人工核实或发布供应报价、采购条件与物流报价，严格区分单次报价与长期条件，完整支持 MOQ 与 `all_units`（全量阶梯）／`graduated`（分段阶梯）计价。
   - **`CST`（核价 · 核心域）**：以纯函数规则链计算可复现的成本评估场景，冻结为不可变成本快照（绑定全部配置、汇率、供应条件版本哈希）。若上游来源事后被否认，守卫机制自动标记快照不再可采纳，防止用过期或作废成本对外报价。
   - **`TRD`（报价与审批 · 核心域）**：工作稿冻结为带服务端计算结果与商业哈希（`business_hash`）的报价修订；编制人与审核人严格职责分离；毛利率低于政策阈值时必须走独立的**毛利例外审批**（普通内容批准不可覆盖）；正式化须严格满足有效期 `as_of < expires_at`，生成带编号的正式报价单。

3. **流 ③ · 客户签约、外销订单与变更上限（`TRD 确认与订单`）**
   - **合同成立与内部审批分离（`ADR-BR-013`）**：人工核实客户回复后，依据适用法律配置的**到达规则**判定合同成立时间——只要可核实的到达早于报价到期，合同即成立，事后报价到期不阻断内部订单审批。
   - **双订单形成模式**：默认 **`full_v1`** 保证一份报价根只形成唯一外销订单（准备时永久占用名额，禁止再替代或作废报价）；在冻结时显式选择 **`multi_order`** 后，可通过人工专属命令 `order.prepare_partial` 按行分批多次下单，并在并发竞争中保证总额绝不超出行上限。
   - **订单生效守卫与变更约束**：订单生效须通过独立的订单审批、逐项确认准备后出现的上游风险，并同步通过 `STL` 客户信用守卫与 `CNX` 贸易合规守卫。生效订单只通过独立审批的**订单变更**形成新修订，变更数量不得低于已确认出运量（`TRD-INV-018`），且在 `multi_order` 报价上变更增加量不得超出该行剩余上限（`8066e1c`：`QUOTE_REMAINING_INSUFFICIENT`），减少或取消不退回已占名额（`TRD-INV-019`）。

4. **流 ④ · 采购分配、条件库存／委外、质检与双路线出运（`PUR` → `STK`/`MFG` → `QLT` → `FUL`）**
   - **`PUR`（采购与供需分配 · 核心域）**：从生效订单行按需分配采购量（支持同一订单行拆分给多家供应商，防超分与已发生守卫）；不可变采购草稿经独立审批重算后签发采购承诺；供应商直发交付须由另一名人工核实，形成 `SupplierDeliveryGuard v2`（`R82`）。
   - **`STK`（库存与外厂台账 · 按公司默认关闭）**：通过 `stk.module.configure` 开启后，提供收发调整、预留、FIFO 批次成本层与 `StockAvailability v1` 并发出库守卫；采用直发路线时绝不虚构本仓库存移动。
   - **`MFG`（生产协同与部分委外 · 按公司默认关闭）**：通过 `mfg.module.configure` 开启后，支持协作计划、工序委外单发出与材料交接（依赖 `STK`）。`8066e1c` 补齐了发出前先锁协作计划 `FOR UPDATE`、校验未取消委外累计数量不得超过工序量与所引 PUR 需求，以及交接货号不属于计划材料时在库存移动前拒绝（`REFERENCE_INVALID`）。外厂进度仅记为来源声称，绝不直接写出库存、质检放行或出运。
   - **`QLT`（质量检验与放行）与 `FUL`（履约出运）**：`QLT` 维护检验、不合格处置与质量放行，并由 `FUL` 扣减已消费放行量（`R79`）；`FUL` 管理订舱、直发／库存双路线出运、五重商业条件放行、出口批次及中英双语商业发票／装箱单签发（CIF／CIP 条款强制足额保险校验）。

5. **流 ⑤ · 业务结算、中国协同与售后闭环（`STL` → `CNX` → `CLM`）**
   - **`STL`（业务结算 · 核心域）**：维护客户信用额度（新客户默认 `0`，赊销订单生效前预占额度）、不可变应收应付、商业资金收付记录、部分核销与撤销核销、费用分摊、贷项通知单与冲销、期初余额，以及订单经营结果核算（直发按采购成本、本仓按 `STK` FIFO 成本层）。
   - **`CNX`（中国出口专业协同）**：管理贸易合规核查、出口许可证登记／分配／释放、购进发票导入与核实、出口报关资料与渠道提交／回执／对账、退税资料多对多用途分配、原产地与检验证书及期初退税资料。`8066e1c` 开放了 5 条报关与退税渠道 HTTP 命令。
   - **`CLM`（售后与索赔）**：支持索赔立项、退货登记（作为 CLM 独立事实，绝不篡改原出运记录，R1 不自动回写库存）、补救裁决（同一批准补救仅允许生成一次贷项，防重复过账 `CLAIM_REMEDY_ALREADY_SETTLED`）及结案；存在未结索赔时，经营结果的索赔维度不满足，自动阻止 `order_result.close`。

## 03 核心业务机制与 BRC-001 全链路核算实例 {#s3}

为了将抽象的领域规则落到每一分钱与每一件货上，Brant 使用贯穿全链路的合成核算基准 **`BRC-001`**，在 PostgreSQL 16 集成套件中通过 HTTP 完整重放，验证数量守恒、金额守恒、权限独立与状态跃迁。

{{pm_brc001 fig="FIG 02"}}

### 3.1 从询价到净利 300.00 USD（31.25%）的确定性账本

1. **需求与单价**：客户询价含 4 条服装款色码明细（`ST01.red.S` 24、`ST01.red.M` 36、`ST01.blue.S` 12、`ST01.blue.M` 48），合计 **`120 PCS`**，单价 `8.00 USD`，净销售额 **`960.00 USD`**。
2. **成本与采购**：供应商报价单价 `5.00 USD`（采购成本 `120 × 5.00 = 600.00 USD`），叠加固定分摊物流费用 `60.00 USD`，`CST` 冻结成本快照 **`660.00 USD`**；`PUR` 编制并审批采购承诺 **`600.00 USD`**。
3. **毛利与例外门槛**：精确计算毛利 `960.00 − 660.00 = 300.00 USD`，毛利率 **`31.25%`**。按最低毛利率 `25%` 校验（精确有理数比较 `R − C ≥ R × 25%`，不先舍入毛利率），最低免审批收入线为 `880.00 USD`；若报价 `879.99 USD` 立即触发 `requires_approval`，须由非销售、非核价的独立**毛利审批人**放行。
4. **付款分期与信用占用**：付款条款为 30% 预付 ＋ 70% 出运后收款，最大余数法分配得 **`288.00 USD` ＋ `672.00 USD`**（总和与应付严格守恒）。订单生效前，`STL` 信用守卫对出运后到期部分预占信用额度 **`672.00 USD`**。
5. **履约与经营结果**：出运确认、资金核销完成后，`STL` 依据不可变台账汇总订单经营结果：净收入 `960.00 USD`、履约成本 `660.00 USD`、经营净毛利 **`300.00 USD`（`31.25%`）**；若中途发生客诉索赔，须完成补救贷项与索赔结案后，经营结果才允许关闭。

### 4.2 任务双轨控制与可随时接管的停止屏障

`TSK` 上下文将**任务生命周期**与**控制权归属**彻底解耦：

- **13 个任务生命周期状态**：`created` → `scoping` → `running` → `waiting_input` ／ `waiting_approval` ／ `waiting_external` ／ `verifying` ／ `paused` ／ `stopping` → `completed` ／ `closed_unfulfilled` ／ `cancelled` ／ `failed`。
- **独立控制模式与单调纪元**：`control_mode` 在 `ai` 与 `manual` 之间切换，`control_epoch` 单调递增。负责人随时可接管任务：任务先进入 `stopping` 停止屏障等待在途模型调用结束，确认停止后转为人工接管；**接管绝不回滚此前已经合法提交的业务事实**，后续不再产生任何模型调用。
- **三段执行回执与权威完成判定**：任何业务动作严格区分 `ACCEPTED`（已受理）、`COMMITTED`（已落库）、`VERIFIED`（已核验）。任务目标 `quote_ready` 与 `order_active` 只能由 `TSK` 读取 `TRD`/`INQ` 权威数据库记录核验通过才能进入 `completed`，**模型自述“订单已生效”绝对无效**（现场评测 `an11` 5/5 全部拦住）。

### 4.3 三道不可绕过的 AI 安全防线

1. **F2 传输层硬拦截**：`internal/transport/httpapi` 对每一条写 HTTP 路由强制前置检查——只要已验证 OIDC 令牌的 `actor.kind == ai`，在**读取请求体之前**即返回 `403 PERMISSION_DENIED`（路由遍历测试锁住，现场对抗 `an10` 5/5 全部拦截）。
2. **进程内能力网关（`internal/ai/gateway`）**：`brant-worker -agent` 在进程内调用网关，逐项校验 `ExecutionBundle` SHA-256 兼容性（`ct14` 5/5 实测 0 调用即暂停）、有效未撤销的委托、命令不在 128 条人工专属清单内、严格 JSON Schema 以及实时任务预算。敏感配置（如 `bank_account`）硬性排除在 AI 只读能力之外。
3. **内容绑定批准授权（`agp.*`）**：高风险受控动作（如 `order.prepare`、`order.review.request`）必须先生成提案，人工审批人审阅具体对象 ID、修订号与规范化载荷 SHA-256 后签发一次性批准授权；任何参数改动导致哈希失配即被拒绝；委托一旦撤销任务立即暂停（`an04` 5/5 通过）。

## 05 风控、合规、放行闸门与职责分离体系 {#s5}

外贸企业最大的经营风险往往不是“少记了一笔账”，而是**越权审批、带病出运、对受制裁主体或无证商品发货、以及绕过信用控制赊销**。Brant 将这些风控要求直接编译进领域守卫与权限引擎，不依赖操作员自觉或页面隐藏按钮。

{{pm_release_gates fig="FIG 04"}}

### 5.1 五重同步商业放行闸门与交易守卫

在订单生效（`order.activate`）和出运放行（`shipment.confirm`）两个最关键的对外履约闸口，系统在同一数据库事务内通过上游守卫函数执行 `FOR SHARE` 实时复核：

- **质量闸门（`QLT`）**：核验有效质量放行结论与剩余可放行数量（`R79`），防止一份合格检验报告被多次出运超量复用。
- **信用与付款条件闸门（`STL`）**：新客户默认信用额度为 `0`，含出运后收款条款的订单须先占用信用额度再生效；出运前重查合同付款条件满足情况，付款条件例外**只能由信用经理批准，销售岗位严禁放行信用**。
- **主体筛查闸门（`PTY` ＋ `ref`）**：新主体在未完成筛查前处于 `pending` 状态；名单由合规岗位受控导入（上限 `32 MiB`）并按合规法规显式启用适用来源（遵循 `ADR-BR-017` 对外国制裁名单审慎启用原则）；过期或未通过结论自动阻断出运。
- **贸易合规与许可证闸门（`CNX`）**：订单生效与出运放行须有覆盖**当前订单修订**的 `clear` 贸易合规结论及有效出口许可证占用；**合规结论为 `blocked` 时，任何角色都不能通过例外覆盖强行放行**。
- **供给与库存守卫（`PUR` ／ `STK`）**：直发路线严守不超过已核实供应商交付量（`SupplierDeliveryGuard v2`）；本仓路线锁住库存行校验可用库存并按 FIFO 成本层扣减（`StockAvailability v1`）。

### 7.1 架构分层与并发一致性设计

- **编译期边界强制守护**：`cmd/` 仅导入 `internal/bootstrap`；`internal/kernel` 仅依赖 Go 标准库；`internal/foundation` 禁止导入任何业务上下文；上下文 `api/` 仅依赖标准库与 `kernel`；跨上下文仅允许按 Context Map 上游方向导入 `api/`（`82` 条允许关系由 `make allowlist` 自动生成，当前 **215 个 Go 包 0 违规**）。
- **无死锁事务锁序**：每个上下文独占自己的 `brant_<bc>` Schema 与 `bentopg.DB`，严禁嵌套调用其他上下文的事务 owner。事务内严格遵循「先以 `FOR UPDATE` 锁本聚合根，再调用上游守卫函数以 `FOR SHARE` 锁上游守卫行」，全部 **26 条守卫锁边经构建器静态证明无环**。
- **原子事件分发与死信治理**：**137 种集成事件**与聚合写入在同一 PostgreSQL 事务中落入 `bento.outbox`；由 2–3 个 `brant-worker -dispatch` 进程按分区租约并发分发给 **8 个系统消费方**（以事件 ID 幂等去重）；连续失败达阈值后自动隔离至 `brant_msg` 死信表并触发独立告警，由授权人工按事件 ID 发起受控重放（`ADR-BR-015`）。
