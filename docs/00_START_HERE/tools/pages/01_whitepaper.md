<h2>以完整业务关系约束研发，以确定性规则和可核验证据交付 AI 原生外贸运营</h2>

- 产品 | IDP Brant · AI-Native Trade Operations Platform（AI 原生外贸业务运营平台）
- 首发配置 | 中国境内单一经营主体、B2B 自营一般贸易货物出口（CN-M01），默认成品采购供给（S01）

## 00 执行摘要 {#s0}

:::cards
- 定位 | 一个系统贯通外贸经营 | 从询价、寻源、核价报价、订单，到采购及生产协同、质量、出运、结算与售后，Brant 维护业务事实与规则，AI 负责资料理解与受控任务协作。
- 边界 | 事实只有一个写入方 | {{=contexts}} 个候选限界上下文分别拥有主体、商品、商业政策、询价、供应条件、核价、报价与订单、采购、结算等事实；跨上下文只按引用与版本协作。
- AI | 意图到真实结果 | 首发必须有一条从意图到真实业务结果的 AI 主链（Q01）；AI 产生候选并走与人工相同的命令路径，人工核实、审批与正式化不可由 AI 代替。
- 证据 | Python 证明规则可行 | Python V0.50 用 50 多个迭代版本固化了报价、审批、客户确认、订单与采购草稿的规则，679 项测试在本机重跑通过；这些规则是 Go 实现的行为基准。
:::

最重要的结论有三条：

1. **范围不变，载体换成 Go。** 产品范围、事实归属与验收组织沿用基线 V1.0；业务核心改为 Go 实现，Python V0.50 降为行为参考。
2. **先裁决一致性策略，再写代码。** Brant 的设计要求报价正式化、订单激活与成本冻结在同一事务里重查上游事实；Cargo 的仓库基线与 idp-bento-go 的事务机制禁止跨上下文的事务内读取。这一冲突登记为 ADR-BR-004，是 G1 的阻断项。
3. **以等价性推进迁移。** S1—S3 三个切片分别以 Python 的 T01＋共享基础、T02、T03＋T04 行为等价为退出条件；{{=pythonUniqueTests}} 个唯一 Python 测试方法已映射到目标上下文，移植与通过分开登记。

## 01 产品定位与目标客户 {#s1}

Brant 面向中国境内 B2B 出口企业，管理从询价、寻源、核价报价、订单，到采购及生产协同、质量、出口履约、业务结算和经营分析的业务关系。首发以单一经营主体、自营一般贸易货物出口为基准，服装作为首个行业配置方向。

| 维度 | 定义 | 边界 |
|---|---|---|
| 目标客户 | 中国 B2B 出口贸易企业（首发默认成品采购供给） | 完整自制制造、集团多主体、复杂代理与加工贸易不在默认首发范围 |
| 核心价值 | 报价与订单承诺正确、可追溯；供应组织与履约受控；结算可解释 | 不承诺未实测的人效、成交率或营收数字 |
| AI 角色 | 资料理解、方案组织、受控动作与结果核验 | 不拥有交易事实，不自行批准，不扩大授权 |
| 专业办理 | 资料准备、匹配、核实、差异与结果归档由 Brant 组织 | 正式报关、开票、退税申报、银行与外汇办理由获准专业系统或授权人员完成 |

> [!evidence] 客户证据状态
> 基线要求进入真实试点前取得至少一笔普通出口与一笔变更或异常业务的脱敏资料。当前有合成样例 BRC-001 与模拟 G0 走查（04 阶段第 08 章：3 个虚构业务、6 项发现均已处置），但没有真实客户资料，因此 G0（客户场景确认）仍为 NO-GO。这不妨碍受控的 P0 研发，但阻断真实客户试点。

## 05 事实权威与业务边界 {#s5}

每项关键业务事实恰好有一个写入方，其他上下文只能通过公开命令、查询或事件使用它。下面是首发最关键的几条，完整的 {{=factAuthority}} 条权威矩阵见 03 阶段。

| 事实 | 唯一写入方 | 其他上下文的使用方式 | 禁止 |
|---|---|---|---|
| 外部主体身份与交易角色 | PTY | 按 PartyRef（kind＋id＋row_version）引用并重查当前版本 | 下游复制主体档案作为权威 |
| SKU 身份与规格修订 | CAT | 按 SkuRef 引用 | 自动创建未知 SKU |
| 汇率、税价口径、核价政策、模板 | POL | 按 ConfigRef 引用并检查当前效力与有效期 | 缺失汇率默认 1；按同名条款推定相等 |
| 客户需求 | INQ | ready 询价及完整行 | 改行凑平源数量冲突 |
| 供应报价与采购条件 | SUP | 当前有效修订 | 单次回复自动成为永久条件 |
| 成本快照与可采纳资格 | CST | 新动作重查可采纳资格 | 未核实预览冒充可报价成本 |
| 报价修订、批准、客户接受与合同成立、外销订单及其变更、外销合同／形式发票 | TRD | 订单、订单修订与目标核验事实对下游发布 | 管理员或连接器直接设置 active；以内部审批时间否定已成立的合同 |
| 采购草稿、承诺与直发交付 | PUR | 结算与发票匹配引用；出运引用已核实的直发交付 | 草稿被当作已向供应商下单；供应商上报被当作已交付 |
| 业务应收应付与核销、付款条件满足、客户信用额度与占用 | STL | 报表汇总，不另建余额；付款条件以守卫向 FUL 发布，信用占用以守卫向 TRD 发布 | 商业核销被称为出口收汇核销；付款计划冒充到账；无占用生效赊销订单 |
| 出运与单证放行、订舱与出运单证 | FUL | 读取质量放行、付款条件与主体筛查守卫后放行 | 以普通备注放行 |
| 主体筛查结论 | PTY | 订单生效与出运放行前读取当前结论 | 以 AI 判断或过期结论放行 |
| 贸易合规核查（国别禁运、制裁、出口管制）与出口许可证用量 | CNX | 订单生效与出运放行前读取当前订单修订的结论与许可证分配 | 以旧修订结论或过期许可证放行 |
| 报关、开票、退税、银行结果 | 外部专业系统 | CNX 保存原文与映射版本 | 导出文件冒充专业办理成功 |

> [!decision] 交易事实属于公司
> 所有权威业务记录带 tenant_id 与 company_id；外部主体与公共商品按已定义范围共享。首期只允许一个启用经营主体，第二主体、跨公司库存分配与资金核销返回明确“不支持”。

## 06 AI-Native 产品原则 {#s6}

产品基线已把 AI-Native 定为首发要求：首发必须交付至少一条从意图到真实业务结果的 AI 主业务链；只有资料识别、聊天问答或草稿补全不满足要求。AI 承担不确定的理解与组织工作，确定性规则由业务服务维护。

:::cards
- Q01 | 询价到可执行报价，再到授权订单 | 接收任务、识别需求、建立上下文、形成方案、审核报价、报价落地、等待回复、订单落地、核验结果九个阶段，每阶段有必须形成的证据。
- 目标 | quote_ready 与 order_active | quote_ready 表示经审批的有效报价与正式文件已保存，不声称客户已收到；order_active 表示有足够客户确认依据且授权满足的订单已生效并通过核验。
- 任务 | 生命周期与控制权分开 | BusinessTask 有 13 个生命周期状态；control_mode 为 ai 或 manual，control_epoch 单调递增；接管经 stopping 屏障，已提交事实不回滚。
- 核验 | 完成只看权威记录 | completed 只能经目标断言核验进入；模型自述、客户端 completed=true 或中间草稿都不能代替。
:::

| 原则 | 规范性要求 | 可证伪的验收 |
|---|---|---|
| 同一命令路径 | AI 与人工调用同一 Go 应用服务；聚合与数据库事务维护事实 | AI 不得直连仓储或数据库 |
| 人工专属命令 | 主数据核实、询价范围核实、报价冻结与审批、正式化、客户接受核实、订单审批与变更、采购草稿编制与作废、放行只接受人工身份；完整清单以 05 阶段 humanOnlyCommands 为唯一来源 | AI 身份即使有通配授权也被拒绝 |
| 候选不是事实 | 解析、匹配与分类结果是 AI 候选，经人工或确定性规则确认后才进入命令 | AI 分类的 full_unconditional 不能自证客户接受 |
| 执行三段回执 | ACCEPTED、COMMITTED、VERIFIED 分开 | 错误宣称完成的用例必须失败 |
| 人工节点显式 | 无渠道时人工发送或导入回复显示为人工节点并计入效率评测 | 人工搬运不被统计为自动化 |
| 恢复不重复 | 稳定 action_id、幂等命令与对账；提交后断连先读结果 | 提交成功后进程宕机不重复创建业务结果 |

Brant 沿用 Cargo 的结论：AI 能力网关、委托策略、审批凭证、执行回执与评测放在 internal/ai，不是限界上下文。与 Cargo 不同的是，业务任务（BusinessTask）对人工与 AI 驱动都成立，作为 TSK 上下文登记（ADR-BR-003）。

## 07 确定性业务规则 {#s7}

以下规则是领域核心，不允许由 AI 或界面替代。Python V0.50 已实现其中多数，Go 与之保持等价；标注“有意背离”的条目按本档案 05 阶段执行，不移植 Python 的行为。

| 规则域 | 规则 | 来源 |
|---|---|---|
| 精度 | 数量 6 位、单价 8 位、汇率 12 位、比例 8 位小数上限；计算至少 34 位有效数字；超限拒绝，不静默截断 | 基线 4.1；T02 §3 |
| 舍入 | 金额按币种最小单位 HALF_UP；行金额先舍入再求和；含税拆分以应付守恒 | T03 §5.1 |
| 汇率 | 明确方向与用途（cost_estimate、quotation）；同币种明确 1；不默认、不反向、不交叉推导 | 共享基础规格第 4 条 |
| 税价 | 销售税须有独立的适用依据；购进成本口径不能冒充销售税；采购税额按核实口径全额、部分或不可回收，部分回收按经核实的可回收率计算；未知回收处理阻断 | T03 §5.1；T02 §13.3；CST-INV-007 |
| 毛利 | 精确比较 R−C ≥ R×minimum_margin；低于阈值为 requires_approval，须独立的毛利例外批准，普通内容批准不覆盖（有意背离：Python 无例外通道） | T03 §5.2；TRD-INV-007 |
| 付款 | 阶段比例合计 100；金额按最大余数法分配并与应付守恒；不生成应收或到账 | T03 §5.3 |
| MOQ 与阶梯 | MOQ 按实际采购量与明确分组；all_units 与 graduated 分别计算；不自动超采，超采须显式标记并批准；同一订单行可分配给多家供应商（有意背离：Python 一行一草稿） | T02 §5、§13.1；PUR-INV-002／005 |
| 费用 | 同一费用义务不重复计入；包含关系不再相加；范围不明返回 CHARGE_SCOPE_UNRESOLVED | T02 §6 |
| 有效期 | 报价正式化与批准 as_of < expires_at，相等拒绝；不得在激活时延长有效期或复用旧批准。客户承诺按可核实的到达时间判定，到达早于到期即合同成立，之后报价到期不阻断订单（有意背离：Python 以核实时间判定） | T03 §4；ADR-BR-013 |
| 审批 | 批准绑定修订、商业哈希、动作与政策；审核人独立于编制人；激活时重查审核人资格 | T03 §6；A33—A35 |
| 转单 | 同根 full_v1 唯一订单，prepare 时永久占用，占用后禁止替代或取消报价 | 核心设计 8.3 |
| 订单审批 | 订单生效需要独立于报价批准的订单审批；审批有效期与报价有效期无关，准备后出现的上游风险须逐项确认；撤销阻止新激活，不倒写已激活订单 | A38—A41；TRD-INV-014 |
| 订单变更与终止 | 生效订单只经独立审批的订单变更形成新修订，数量不低于已确认出运量；取消须无出运且下游承诺已解除；短交关闭与关闭保留名额与历史 | 基线 3.3；TRD-INV-018／019 |
| 商业条件放行 | 出运与单证放行须质量放行、合同付款条件、主体筛查与贸易合规（含许可证）同时满足；付款条件例外须授权人工批准，合规 blocked 不能被例外覆盖；直发出运不超过已核实的供应商交付量 | 基线 F29、BT13；FUL-INV-002／003 |
| 信用与合规 | 付款条件含出运后到期部分的订单，先在 STL 占用信用额度再生效；超额或逾期超限生成信用决定，按金额层级由非销售的信用人员放行，新客户默认额度为 0；订单生效须有覆盖当前修订的贸易合规结论 clear；名单只启用适用来源，新主体筛查前为 pending | ADR-BR-016／017；STL-INV-004／005；TRD-INV-022／023；PTY-INV-002 |

## 08 Go DDD 总体架构 {#s8}

Brant 采用单仓库、单 Go Module 的模块化单体与六边形架构。{{=contexts}} 个候选上下文是模型适用范围，不是部署单元；每个上下文在 Go 中是 internal/contexts/<bc>/{module.go, api/, internal/}，由编译器守住边界，由 Context Map 生成的 import 白名单约束依赖方向。

> [!warn] 阻断项：跨上下文的事务内资格重查
> Python 在单个 SQLite 事务（BEGIN IMMEDIATE 全库写串行）里重查成本快照、配置效力与审核人资格，保证“反证先提交则拒绝”。Go 基线要求每个上下文独立事务 owner，idp-bento-go 在另一个 owner 的事务中开事务会直接返回 transactionConflict，且默认隔离级别为 READ COMMITTED。三个候选方案与裁决要求见 03 阶段 ADR-BR-004 和 12 阶段第 9 章。严格的“反证先提交则拒绝”只对对外承诺之前的正式化与冻结必需；订单生效发生在合同成立之后，上游变化作为由订单审批确认的风险处理（ADR-BR-013）。

## 09 中国出口首发配置 {#s9}

默认首发配置为 CN-M01：境内单一经营主体、自营一般贸易货物出口。Brant 必须能组织获准出口业务的资料、匹配、差异、责任与外部结果；正式报关、开票、退税申报、银行与外汇操作由专业系统或授权人员执行，人工路径同样需要证据、版本、对账与成本记录。

| 控制规则 | 设计约束（摘要） |
|---|---|
| CN-R02 单位与金额口径 | 成交、库存、开票与法定单位分别保存；成交价、申报价与分析口径区分 |
| CN-R03 税价分离 | 可抵扣、可退与不可收回税额依实际政策核实；不得把全部采购税计成本又把预计退税计利润 |
| CN-R05 外部状态 | 本地草稿、导出、人工提交、外部受理、放行或核准、资金到账各自区分；unknown 先查证 |
| CN-R07 报关变更 | 海关放行、实际离境、物流送达与客户验收是不同事实 |
| CN-R08 退税状态 | 预计、拟申报、已提交、核准与到账分别记录 |
| CN-R11 银行操作边界 | 系统内核销只是商业资金分配，不得称为行政意义的出口收汇核销 |

中国配置的八项待决项（CN-D01—CN-D08：经营模式、税务办法、商品申报、票据、银行、专业系统、成本税额、单证期限）尚未冻结；在冻结之前，相关业务只允许保存草稿，不允许自动判定合规或完成专业办理。
