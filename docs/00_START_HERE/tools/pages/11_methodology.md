<h2>用业务事实驱动架构，用反例与证据控制交付</h2>

<p class="lede">本手册是 Brant 版的 DDD 方法论。它沿用 IDP-Cargo 方法论 Go AI-Native V2.0 的原则（七步闭环、证据分级、事实权威、Go 原生工程规范、AI 受控执行），并补上 Brant 特有的三件事：审批与人工核实的通用方法、Python 参考实现到 Go 的等价纪律，以及外贸场景的两个参考案例。</p>

::: cover
- 适用对象 | Brant 的领域专家、架构师、领域工程师、QA 与 AI 集成团队。
- 与 Cargo 的关系 | 原则相同，案例与规则换成外贸业务；冲突时以本手册与 Brant 的 ADR 为准。
- 模板 | 02_METHOD_TEMPLATES 下 7 份模板，已填入 Brant 示例行。
:::

| 规范性条款 | 要求 | 可验证的验收 |
|---|---|---|
| 不绕过 DDD | AI 与界面共用 Go 应用服务；聚合与数据库事务维护业务事实 | AI 不得直连仓储或数据库 |
| 执行与验证分开 | ACCEPTED 不等于 COMMITTED，COMMITTED 不等于 VERIFIED | 错误宣称完成的用例必须失败 |
| 人工专属命令 | 核实、审批与正式化只接受人工身份 | AI 身份带通配授权仍被拒绝 |
| 等价先于重写 | Python 已验证的规则以映射用例移植并通过 | 映射表每行都有结论 |
| 一致性先于代码 | 跨上下文资格重查策略在写代码前裁决 | ADR-BR-004 有签核记录 |

## 00 执行摘要 {#s0}

外贸运营不是表单 CRUD。同一笔生意里，谁承诺价格、谁批准内容、谁核实客户接受、谁对供应商作出采购承诺、谁确认实际出运、谁维护应收与核销，都是不同的责任与生命周期。本方法论要求：每项关键事实恰有一个写入方；每条重要规则都有能失败的测试；每个“通过”都注明证据等级；每个边界争议都有 ADR。

:::cards
- 01 | 语义先于表结构 | 先在上下文内统一“报价”“确认”“审批”的含义，再设计表。
- 02 | 事实权威先于接口 | 先确定谁能纠正一项事实，再决定谁调用谁。
- 03 | 不变量先于事务 | 先写出必须同时成立的规则，再确定聚合与锁。
- 04 | 证据先于结论 | 区分 Python 参考、结构校验、Go 单元、PG16 集成与业务签核。
:::

## 01 为什么 Brant 需要 DDD {#s1}

| 复杂度来源 | Brant 中的例子 | 不用 DDD 的后果 |
|---|---|---|
| 同词异义 | 对客报价、供应报价、物流报价；主数据核实、客户接受、供应商确认 | 一个 status 字段承载多种含义，审批与生效互相冒充 |
| 状态不同步 | 报价 active 与客户接受、订单生效、采购承诺各自独立 | 用一个流程状态代替多个事实，历史被覆盖 |
| 法规与专业边界 | 报关、开票、退税、收汇由专业系统或授权人员办理 | 导出文件或任务完成被当作专业办理成功 |
| 金额与币种 | 成本按 cost_estimate 汇率，比较按 quotation 汇率，客户付报价币种 | 汇率默认 1、自动反向或混币求和 |
| 异常与纠错 | 批准撤销、来源否认、报价替代、订单准备后到期 | 静默改写已提交事实，或重复转单 |
| AI 参与 | AI 生成候选、组织步骤、调用同一命令 | 模型输出直接变成业务事实 |

DDD 不是微服务规范：上下文是模型适用范围，聚合是事务一致性边界，部署单元另由证据决定。Brant 以模块化单体起步。

## 02 科学性与证据原则 {#s2}

科学性来自可证伪的业务假设：提出假设，构造反例，执行验证，在证据不足时保留待决状态。

| 等级 | 证据形式 | 能支持的结论 | 不能声称 |
|---|---|---|---|
| E0 假设 | 设计草案、本档案的 DDD 资产 | 可以启动反例验证 | 客户真实流程 |
| E1 领域事实 | 脱敏业务单据、专家访谈、法规来源与反例 | 业务行为已被讨论 | 代码符合 |
| E2 工程证据 | Schema、单元与契约测试、可复现日志（含 Python 参考测试） | 参考实现或模块行为符合断言 | 真实数据库与外部集成通过 |
| E3 系统集成 | PostgreSQL 16、IAM、渠道与专业系统联测 | 指定环境与版本的联动有效 | 生产稳态与签核 |
| E4 运行证据 | UAT、审计、监控与真实业务复盘 | 指定范围的运行表现 | 无条件外推 |

裁决记录的最小格式：假设 → 边界 → 反例 → 证据引用 → 结果 → 专家决定 → ADR → 受影响契约 → 回归测试。

## 03 七步闭环工作法 {#s3}

| 步骤 | 主责 | Brant 的强制产物 | 退出判据 |
|---|---|---|---|
| 01 领域发现 | 产品与业务 Owner | 真实单据、正常与异常流程、决策日志 | 关键流程有正常与异常证据（G0） |
| 02 语言对齐 | 领域专家＋架构师 | UL 词条、冲突记录、状态语义 | 同一上下文一词一义 |
| 03 战略划界 | 架构师＋各上下文 Owner | Context Map、事实权威、关系与 ADR | 每项关键事实恰有一个写入方 |
| 04 战术设计 | 领域工程师 | 聚合、状态机、命令、不变量、锁序 | 并发、撤销、重复与到期场景可表达 |
| 05 工程契约 | 接口、数据与安全负责人 | Schema、错误码、事件、schema 归属 | 契约与负向例自动化 |
| 06 实施验证 | 开发、QA、SRE | Go 模块、迁移、PG16、CI、等价性报告 | 门禁达标、边界检查通过 |
| 07 反馈演进 | 产品、业务、架构 | 异常复盘、模型修订、ADR | 变更可追溯、兼容策略明确 |

对一条可验收的业务切片执行完整循环，而不是先为全部 18 个上下文设计所有表与服务。Brant 的第一条切片是主数据与询价（S1）。

## 04 子域与上下文识别 {#s4}

先找业务问题与语义变化，再决定边界；不要把部门、菜单、数据库 schema 或 Python 的交付切片（T01—T04）直接当成上下文。识别边界的五个问题：

1. **语义**：两个团队说“确认”时，是否指同一种责任与生命周期？
2. **不变量**：哪些规则必须在一个命令中立即成立？
3. **事实权威**：两边结果不同时，谁有权纠正？
4. **变更原因**：规则是否由不同的业务、财务或法规 Owner 决定？
5. **协作方式**：能否用稳定的事实、命令与版本化契约协作？

评分卡（模板 03）每项 0—2 分，只用于促进讨论。Brant 的典型结论：报价与订单因共享报价根锁序而合并（5 分），业务任务因语义与生命周期完全独立而单列（10 分）。

## 05 统一语言治理 {#s5}

词条强制字段：词条 ID、上下文、中英文、定义、禁止混同、规则引用、来源证据、状态、Owner、版本。命名在代码、接口、事件、日志与报表中保持一致，不得无痕更名；冲突词（审批、确认、报价、订单、放行、核销、发票）必须登记处置规则。词条批准逐条记录，不能只升整个文件的版本号。

## 06 事件风暴工作法 {#s6}

| 步骤 | 主持人操作 | Brant 示例 | 产出 |
|---|---|---|---|
| 收集凭证 | 用询价原文、供应报价、报价单、客户回复串时间线 | BRC-001 | 事实清单 |
| 写过去时事件 | 不猜数据库状态 | QuoteActivated、AcceptanceVerified | 事件与时点 |
| 定位命令与角色 | 谁能发起、谁可拒绝 | quote.review.decide 只能由独立人工执行 | 授权与前置条件 |
| 放置策略与超时 | 何时可以继续、何时阻断 | 报价到期后订单激活阻断 | 时效守卫 |
| 注入反例与并发 | 重复、乱序、撤销、替代 | 替代与转单并发 | 不变量与冲突处理 |
| 标出边界与未知 | 双重 Owner？ | 成本否认与报价激活谁先 | ADR 候选 |
| 转为自动验收 | Given／When／Then | BC-AT15 | 参考用例 |

## 07 Context Map 与事实权威 {#s7}

关系类型沿用 Cargo：OHS＋Published Language、Customer／Supplier、ACL、Partnership、Conformist、Shared Kernel（只限值对象）。Brant 新增“Qualification Guard”标注：下游在提交前必须重查上游事实的当前资格，其实现方式由 ADR-BR-004 决定。Context Map 必须写出上下游、事实权威、契约与“禁止跨域直接写表”的规则；关系表同时是 Go import 白名单的唯一来源。

## 08 战术建模与 Brant 模式 {#s8}

四类模型元素：实体（持续身份与生命周期）、值对象（以值相等、不可变，如 Money、Quantity、ValidityInterval）、聚合（一个事务内维护必须立即成立的不变量）、领域服务（不自然归属单一实体的纯规则，如分摊）。

Brant 在 Python 迭代中形成了几种可复用的模式，Go 实现应保持：

| 模式 | 结构 | 用在哪里 |
|---|---|---|
| 根＋不可变修订＋效力 | 根维护 root_version 与指针；修订冻结后不可变；效力独立记账 | QuoteRoot、ConfigurationRoot、SupplierOffer、PurchaseTerms |
| 整稿替换草稿 | 草稿可缺项，已提供的值必须合法；保存不是 PATCH | CustomerRfq、QuoteDraft、CostScenario |
| 内容绑定批准 | 批准绑定修订、哈希、动作与政策，独立效力与撤销 | 报价批准、订单审批、采购承诺审批 |
| 资格派生 | 到期、可采纳、就绪是带 as_of 的派生判断 | QuoteReady、SnapshotAdoptability |
| 提交证据 | 生效动作同事务追加证据（版本、批准效力、授权与控制代次、裁决时点） | 报价激活、订单生效 |
| 风险暂停 | 事后变化登记追加事件并限制前向动作，不改写历史 | 生效后批准撤销、来源否认 |
| 转换名额 | 唯一约束＋根锁保证一个来源只转换一次 | full_v1 |

## 09 不变量、事务与并发 {#s9}

最重要的建模问题不是“建哪些表”，而是哪些不变量必须同时被守护。强一致只在聚合内：命令 → 预期版本 → 守卫 → 变更 → 持久化 → Outbox，同一事务提交。聚合之间与上下文之间最终一致：事件 → Inbox 去重 → 防腐层 → 命令。

Brant 的特殊要求：撤权、纠错、替代、转单、生效与接管使用同一锁序（公司授权守卫 → 根与对象控制 → 修订 → 确认效力 → 订单 → 批准效力 → 动作结果与 Outbox）；持锁期间禁止模型与网络等待；服务器裁决时点在持锁事务末尾采集。Python 依赖 SQLite 全库写串行，Go 在 PostgreSQL 16 上必须用显式行锁与竞争测试重新证明（ADR-BR-011）。

## 10 审批与人工核实的通用方法 {#s10}

Brant 不设通用审批上下文（ADR-BR-005），但所有审批遵守同一方法：

1. **内容绑定**：批准绑定对象、精确修订或快照哈希、目标动作与政策版本；内容变化后旧批准不适用。
2. **独立性**：审核人是授权人工，不属于编制人集合与申请人；AI 参与编制不构成独立复核。
3. **有效期**：带时区，decided_at < expires_at ≤ 被批准对象的有效期；不能倒签或延长。
4. **撤销**：效力独立记账，撤销不删除原批准；撤销先提交则新动作拒绝，动作先提交则保留历史并登记风险暂停。
5. **执行时重查**：生效时重查批准效力、到期、政策当前性与审核人当前资格。
6. **权限分离**：报价审批、订单审批、采购承诺审批、配置发布、外发授权互不替代。

## 11 跨上下文契约与事件 {#s11}

命令契约写明发起者、授权上下文、幂等键、预期版本、失败原因与接收方；领域事件表达本上下文已提交的事实；集成事件通过已发布语言暴露必要事实，不泄露内部实体。投递为至少一次＋幂等＋可重放；补偿使用显式命令，不静默覆盖历史。Brant 的统一事件信封见 05 阶段第 13 章与 06 阶段 Schema。

## 12 Go 工程实施规范 {#s12}

| 依赖控制 | 允许 | 禁止 |
|---|---|---|
| domain | 领域对象、值对象、本上下文的错误与事件 | net/http、pgx、Bento、AI 客户端 |
| application | domain、kernel、Bento application 接口、端口 | 绕过聚合直写其他上下文的表 |
| adapters | 实现端口、仓储、ACL | 让 domain 反向依赖基础设施 |
| 跨上下文 | 已登记上游的 api 包、事件 | 导入对方 internal；跨 schema 写或为写决策 JOIN |
| 部署 | 按证据拆分 | 为“DDD 正统”预建 18 个服务 |

| 评审门禁 | 可执行门槛 |
|---|---|
| 静态 | gofmt、go vet、golangci-lint、dependency-check、漏洞扫描 |
| 领域 | go test ./...；每个关键不变量至少一条拒绝用例 |
| 并发 | go test -race；CAS、幂等、名额、撤销竞争 |
| 数据库 | 真实 PostgreSQL 16：迁移、约束、RLS、Outbox 原子性 |
| 契约 | Schema 兼容与负向载荷；事件重放 |
| 等价性 | Python 映射行全部有结论 |

## 13 Python 到 Go 的等价纪律 {#s13}

Brant 与 Cargo 最大的不同是：Brant 已经有一套经过 50 多个版本迭代、679 项测试通过的 Python 参考实现。方法论因此增加以下纪律：

- **映射、移植、通过分别登记**：映射只说明目标位置；移植说明 Go 用例已编写；通过必须有 Go CI 证据。
- **以唯一测试方法计数**：静态唯一测试方法为 {{=pythonUniqueTests}} 个；679 项包含导入式重复发现，不能用于验收计数。
- **先复现，再修复**：Python 迭代的做法是先写失败测试复现缺口，再修复并保存“修复前”证据。Go 实现遇到行为差异时同样先写失败用例，再决定是修 Go 还是登记 ADR。
- **不按规格重写丢边界**：规格之外的边界情况（如 A26 的文件字节完整性重查、A35 的审批时效）只存在于测试里，必须通过映射保留。
- **规则变化走 ADR**：如果 Go 有意改变某条已验证规则（例如 ADR-BR-004 选择方案 A），对应映射行标记 SUPERSEDED 并写出新断言。
- **证据不混用**：Python 通过不计入 Go 验收；Go 结构校验通过不代表业务签核。

## 14 AI 受控执行 {#s14}

AI 负责资料理解、方案组织与受控动作，业务系统负责事实、金额、权限与状态。AI 输出一律是候选；所有写入走与人工相同的应用服务；执行回执分 ACCEPTED、COMMITTED、VERIFIED 三段；任务完成只看权威记录核验。自治分级（L0—L4）、人工专属命令清单与提示注入防护见 10 阶段第 06 章。AI 能力层（internal/ai）不是限界上下文；业务任务（TSK）是。

## 15 案例 A：报价替代与转换名额竞争 {#s15}

设定：报价根 Q1 的修订 r1 已生效并已有客户接受；修订 r2 已获得目标为 replace 的批准。销售准备订单的同时，另一位经办提交替代。

| 步骤 | 命令 | 上下文 | 可检验条件 |
|---|---|---|---|
| 1 | quote.replace(r1→r2) | TRD | 无转换名额；批准目标与预期旧 active 一致 |
| 2 | order.prepare(r1) | TRD | r1 仍为当前 active；接受有效；名额未被占用 |
| 3 | 两者并发提交 | TRD | 根行锁决定先后，只有一个成立 |

必须演练的反例：替代先提交后 prepare 返回 QUOTE_NOT_CURRENT；prepare 先提交后 replace 返回 ROOT_CONVERSION_LOCKED；用不同请求键重复 prepare 返回 CONVERSION_SLOT_CONFLICT；r2 不能再取名额。退出标准：两种顺序在 PG16 上各运行多次都只产生一个结果，且无死锁。

## 16 案例 B：成本来源否认与当前资格 {#s16}

设定：报价已批准待激活，其成本快照所依赖的供应报价被供应商声明无效，核价经办提交来源否认；同时销售提交 quote.activate。

| 顺序 | 期望结果 |
|---|---|
| 否认先提交 | 激活拒绝（COST_SNAPSHOT_INELIGIBLE），无任何正式化残留 |
| 激活先提交 | 保留合法的激活事实与提交证据；否认之后登记风险暂停，限制新的前向动作（如订单生效） |
| 订单激活 | 同样重查可采纳资格；否认先提交则拒绝 |

这个案例跨越 CST 与 TRD 两个上下文，是 ADR-BR-004 的核心验证场景（SC-04）。方案 A 无法保证第一行；方案 B 依靠 PostgreSQL 行锁保证；方案 C 通过合并上下文保证。裁决前不得实现 S2-06 与 S3-07 的资格守卫。

## 17 可证伪的验证金字塔 {#s17}

## 20 反模式与禁令 {#s20}

| 反模式 | 为什么错 | 修正 |
|---|---|---|
| 一个万能“单据状态” | 报价有效、客户接受、订单生效、已采购、已出运被混为一谈 | 各自的状态机与证据引用 |
| 按 Python 切片建包（t03_*、t04_*） | 交付节奏不是领域边界 | 按上下文与聚合建包 |
| 报价批准冒充订单审批 | 审批对象与责任不同 | 权限与记录分离 |
| AI 自证客户接受或合规 | 无法界定责任 | AI 只产生候选 |
| 汇率缺失默认 1 | 金额错误且难以发现 | 明确方向与用途，缺失即阻断 |
| 事件当远程 UPDATE | 绕过接收方守卫 | 集成事件＋命令验证 |
| 跨 schema 外键或写 SQL | 数据所有权失效 | ID＋快照＋本地投影 |
| 只测正常路径 | 撤销、到期、并发、重放时失真 | 反例、并发与恢复测试 |
| 只按规格重写 Python | 丢失迭代中发现的边界 | 映射驱动移植 |
| 设计校验通过即上线 | 遗漏数据库、身份与业务签核 | 分开 E2 与 E3／E4 |
