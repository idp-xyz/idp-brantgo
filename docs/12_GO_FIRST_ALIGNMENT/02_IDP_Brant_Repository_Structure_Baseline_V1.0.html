01

REPOSITORY STRUCTURE BASELINE

决策摘要

一个仓库 · 一个 Module · 18 个由编译器隔离的上下文

Brant 采用单一产品仓库＋单一 Go Module 的模块化单体。业务代码按上下文组织，每个上下文由 module.go、api/ 与第二层 internal/ 构成编译器级边界；上下文只能依赖 Context Map 登记的上游，写操作不跨上下文共享事务，业务决策留在拥有它的上下文。不为每个上下文建 Module 或微服务；目录随真实代码创建，不预建空脚手架。

相对 Cargo V1.1 的差异Brant 的处理
上下文数量与代码18 个候选上下文（PTY、CAT、POL、EVD、INQ、SUP、CST、TRD、PUR、MFG、QLT、STK、FUL、STL、CLM、CNX、CRM、TSK）
主档案位置docs/ 在仓库内，保存本主档案；Go 构建不引用；若仓库公开，发布时排除 docs/ 或保持私有（ADR-BR-REPO-08）
业务任务TSK 是上下文；AI 能力层仍在 internal/ai，不是上下文（ADR-BR-003）
资格守卫Brant 要求事务内重查上游资格，与 Cargo T3 冲突；GR 规则按 ADR-BR-004 方案 B（模拟评审接受）
首个切片EVD、PTY、CAT、POL、INQ（对齐 Python T01＋共享基础），而非 Cargo 的 ORG→RATE→COM→FUL→BOOK
金额十进制实现须与 Python 精确有理数规则逐分一致（ADR-BR-REPO-10）

REPOSITORY STRUCTURE BASELINE

事务边界与跨上下文协作

idp-bento-go v0.1.0-rc.2 的 WithinTransaction 发现 context 中已有同一 owner 的事务时加入外层事务，owner 不同则返回 transactionConflict；每次 NewDB 生成新的 owner；默认隔离级别 READ COMMITTED。因此是否共享 owner 完全取决于组合根的装配方式，必须写成规则并用测试固定。

编号规则级别
T1bootstrap 为每个上下文调用一次 bentopg.NewDB（可共享一个 pgxpool），不得把同一个 *bentopg.DB 注入两个上下文必须
T2一个事务只修改一个既有聚合实例；聚合写入、命令回执、提交证据与 Outbox 在同一事务提交。同上下文内允许同时创建由本命令派生的新聚合，限于登记的例外：TRD order.prepare 占用名额并创建订单草稿（ADR-BR-002）；TRD quote.response.verify 创建 Acceptance；CST cost_snapshot.freeze 冻结场景并创建快照；PUR purchase.draft.prepare 更新需求分配余额并创建草稿必须
T3对其他上下文的同步调用只允许查询，且在本上下文事务之外发起——资格守卫读取的例外见 GR 规则（ADR-BR-004，模拟评审接受）必须
T4对其他上下文的写入使用上游 api 的命令消息，经 Outbox 与对方 Inbox 投递，携带 CommandID必须
T5投递语义为至少一次；消费方按 CommandID 或事件 ID 去重必须
T6Inbox 分发就绪（S4）之前，跨上下文步骤由 API 客户端、操作员或 TSK 任务逐步发起，每一步只在一个上下文内提交应
T7按 ADR-BR-011 的锁序显式加锁：本上下文聚合根 FOR UPDATE（多根按 ID 排序）→ 同根下级行 → 上游守卫 FOR SHARE（按上下文代码排序，含公司授权守卫）→ 动作结果与 Outbox；以 PG16 竞争测试固定必须

9.1 资格守卫读取规则（GR，ADR-BR-004 模拟评审接受方案 B）

M0-10 在 PostgreSQL 16 上实测了这组规则（M0 执行报告第 05 章）：方案 B 在三种提交顺序下都符合业务设计，方案 A 存在已复现的提交窗口。实测把“守卫视图”改成了“守卫函数”，因为对视图执行 SELECT … FOR SHARE 要求调用方对视图本身有 UPDATE 权限，等于把写权限授予下游角色。

编号规则（ADR-BR-004 方案 B）
GR1守卫契约由上游在 api 中声明（函数名、参数与返回字段），并在自己的 schema 中发布版本化的 SECURITY DEFINER 守卫函数，函数内以 SELECT … FOR SHARE 锁定守卫行，SET search_path = pg_catalog，只向应用角色授予 EXECUTE
GR2下游在自身事务中、以自身 executor 调用守卫函数；不经上游的 DB owner（否则返回 transactionConflict），行锁归下游事务所有，直到其提交
GR3守卫读取只用于拒绝或放行本上下文的写入，不得 JOIN 下游表，不得写入他域
GR4上游撤销以 UPDATE 修改守卫行并递增 eligibility_epoch；下游把观察到的 epoch 写入提交证据；撤销等待持有守卫的下游事务提交后，以事件触发下游的风险登记
GR5每个守卫函数对应 03 阶段关系表中 guardLock=true 的一条关系，并在 dependency-check 与 migration-check（S2 交付）中登记；未登记的跨 schema 读取视为违规
GR6若裁决为方案 A，GR 规则作废：改为事务外预取、提交证据记录观察到的 epoch、上游事件触发风险暂停
GR7守卫锁边（下游以 FOR SHARE 锁上游守卫行）必须构成有向无环图，由主档案构建器校验；导入白名单中的双向关系（如 TRD↔TSK、FUL↔STL）至多一个方向使用守卫锁，另一方向只经事件或事务外查询
