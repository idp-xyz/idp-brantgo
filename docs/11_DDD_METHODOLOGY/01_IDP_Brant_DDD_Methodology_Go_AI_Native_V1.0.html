00

DDD METHODOLOGY

执行摘要

外贸运营不是表单 CRUD。同一笔生意里，谁承诺价格、谁批准内容、谁核实客户接受、谁对供应商作出采购承诺、谁确认实际出运、谁维护应收与核销，都是不同的责任与生命周期。本方法论要求：每项关键事实恰有一个写入方；每条重要规则都有能失败的测试；每个“通过”都注明证据等级；每个边界争议都有 ADR。

01

语义先于表结构

先在上下文内统一“报价”“确认”“审批”的含义，再设计表。

02

事实权威先于接口

先确定谁能纠正一项事实，再决定谁调用谁。

03

不变量先于事务

先写出必须同时成立的规则，再确定聚合与锁。

04

证据先于结论

区分 Python 参考、结构校验、Go 单元、PG16 集成与业务签核。

复杂度来源Brant 中的例子不用 DDD 的后果

02

DDD METHODOLOGY

科学性与证据原则

科学性来自可证伪的业务假设：提出假设，构造反例，执行验证，在证据不足时保留待决状态。

等级证据形式能支持的结论不能声称
E0 假设设计草案、本档案的 DDD 资产可以启动反例验证客户真实流程
E1 领域事实脱敏业务单据、专家访谈、法规来源与反例业务行为已被讨论代码符合
E2 工程证据Schema、单元与契约测试、可复现日志（含 Python 参考测试）参考实现或模块行为符合断言真实数据库与外部集成通过
E3 系统集成PostgreSQL 16、IAM、渠道与专业系统联测指定环境与版本的联动有效生产稳态与签核
E4 运行证据UAT、审计、监控与真实业务复盘指定范围的运行表现无条件外推

裁决记录的最小格式：假设 → 边界 → 反例 → 证据引用 → 结果 → 专家决定 → ADR → 受影响契约 → 回归测试。

04

DDD METHODOLOGY

子域与上下文识别

先找业务问题与语义变化，再决定边界；不要把部门、菜单、数据库 schema 或 Python 的交付切片（T01—T04）直接当成上下文。识别边界的五个问题：

  1. 语义：两个团队说“确认”时，是否指同一种责任与生命周期？
  2. 不变量：哪些规则必须在一个命令中立即成立？
  3. 事实权威：两边结果不同时，谁有权纠正？
  4. 变更原因：规则是否由不同的业务、财务或法规 Owner 决定？
  5. 协作方式：能否用稳定的事实、命令与版本化契约协作？

评分卡（模板 03）每项 0—2 分，只用于促进讨论。Brant 的典型结论：报价与订单因共享报价根锁序而合并（5 分），业务任务因语义与生命周期完全独立而单列（10 分）。

DDD METHODOLOGY

战术建模与 Brant 模式

四类模型元素：实体（持续身份与生命周期）、值对象（以值相等、不可变，如 Money、Quantity、ValidityInterval）、聚合（一个事务内维护必须立即成立的不变量）、领域服务（不自然归属单一实体的纯规则，如分摊）。

Brant 在 Python 迭代中形成了几种可复用的模式，Go 实现应保持：

模式结构用在哪里
根＋不可变修订＋效力根维护 root_version 与指针；修订冻结后不可变；效力独立记账QuoteRoot、ConfigurationRoot、SupplierOffer、PurchaseTerms
整稿替换草稿草稿可缺项，已提供的值必须合法；保存不是 PATCHCustomerRfq、QuoteDraft、CostScenario
内容绑定批准批准绑定修订、哈希、动作与政策，独立效力与撤销报价批准、订单审批、采购承诺审批
资格派生到期、可采纳、就绪是带 as_of 的派生判断QuoteReady、SnapshotAdoptability

09

DDD METHODOLOGY

不变量、事务与并发

最重要的建模问题不是“建哪些表”，而是哪些不变量必须同时被守护。强一致只在聚合内：命令 → 预期版本 → 守卫 → 变更 → 持久化 → Outbox，同一事务提交。聚合之间与上下文之间最终一致：事件 → Inbox 去重 → 防腐层 → 命令。

Brant 的特殊要求：撤权、纠错、替代、转单、生效与接管使用同一锁序（公司授权守卫 → 根与对象控制 → 修订 → 确认效力 → 订单 → 批准效力 → 动作结果与 Outbox）；持锁期间禁止模型与网络等待；服务器裁决时点在持锁事务末尾采集。Python 依赖 SQLite 全库写串行，Go 在 PostgreSQL 16 上必须用显式行锁与竞争测试重新证明（ADR-BR-011）。

DDD METHODOLOGY

审批与人工核实的通用方法

Brant 不设通用审批上下文（ADR-BR-005），但所有审批遵守同一方法：

  1. 内容绑定：批准绑定对象、精确修订或快照哈希、目标动作与政策版本；内容变化后旧批准不适用。
  2. 独立性：审核人是授权人工，不属于编制人集合与申请人；AI 参与编制不构成独立复核。
  3. 有效期：带时区，decided_at < expires_at ≤ 被批准对象的有效期；不能倒签或延长。
  4. 撤销：效力独立记账，撤销不删除原批准；撤销先提交则新动作拒绝，动作先提交则保留历史并登记风险暂停。
  5. 执行时重查：生效时重查批准效力、到期、政策当前性与审核人当前资格。
  6. 权限分离：报价审批、订单审批、采购承诺审批、配置发布、外发授权互不替代。

DDD METHODOLOGY

Python 到 Go 的等价纪律

Brant 与 Cargo 最大的不同是：Brant 已经有一套经过 50 多个版本迭代、679 项测试通过的 Python 参考实现。方法论因此增加以下纪律：

  • 映射、移植、通过分别登记：映射只说明目标位置；移植说明 Go 用例已编写；通过必须有 Go CI 证据。
  • 以唯一测试方法计数：静态唯一测试方法为 577 个；679 项包含导入式重复发现，不能用于验收计数。
  • 先复现，再修复：Python 迭代的做法是先写失败测试复现缺口，再修复并保存“修复前”证据。Go 实现遇到行为差异时同样先写失败用例，再决定是修 Go 还是登记 ADR。
  • 不按规格重写丢边界：规格之外的边界情况（如 A26 的文件字节完整性重查、A35 的审批时效）只存在于测试里，必须通过映射保留。
  • 规则变化走 ADR：如果 Go 有意改变某条已验证规则（例如 ADR-BR-004 选择方案 A），对应映射行标记 SUPERSEDED 并写出新断言。
  • 证据不混用：Python 通过不计入 Go 验收；Go 结构校验通过不代表业务签核。

DDD METHODOLOGY

案例 A：报价替代与转换名额竞争

设定：报价根 Q1 的修订 r1 已生效并已有客户接受；修订 r2 已获得目标为 replace 的批准。销售准备订单的同时，另一位经办提交替代。

步骤命令上下文可检验条件
1quote.replace(r1→r2)TRD无转换名额；批准目标与预期旧 active 一致
2order.prepare(r1)TRDr1 仍为当前 active；接受有效；名额未被占用
3两者并发提交TRD根行锁决定先后，只有一个成立

必须演练的反例：替代先提交后 prepare 返回 QUOTE_NOT_CURRENT；prepare 先提交后 replace 返回 ROOT_CONVERSION_LOCKED；用不同请求键重复 prepare 返回 CONVERSION_SLOT_CONFLICT；r2 不能再取名额。退出标准：两种顺序在 PG16 上各运行多次都只产生一个结果，且无死锁。

DDD METHODOLOGY

案例 B：成本来源否认与当前资格

设定：报价已批准待激活，其成本快照所依赖的供应报价被供应商声明无效，核价经办提交来源否认；同时销售提交 quote.activate。

顺序期望结果
否认先提交激活拒绝（COST_SNAPSHOT_INELIGIBLE），无任何正式化残留
激活先提交保留合法的激活事实与提交证据；否认之后登记风险暂停，限制新的前向动作（如订单生效）
订单激活同样重查可采纳资格；否认先提交则拒绝

这个案例跨越 CST 与 TRD 两个上下文，是 ADR-BR-004 的核心验证场景（SC-04）。方案 A 无法保证第一行；方案 B 依靠 PostgreSQL 行锁保证；方案 C 通过合并上下文保证。裁决前不得实现 S2-06 与 S3-07 的资格守卫。

反模式为什么错修正
